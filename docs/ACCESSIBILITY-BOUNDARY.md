# Accessibility boundary

本文定的是**我们承诺什么、不承诺什么**，不是当前实现的证明。现状跟这条边界之间的差距按普通缺陷追踪。

## 先定前提：breatic 是用鼠标做创作的工具

breatic 是内容创作工具，画布上的拖拽、框选、连线、缩放、裁剪、画笔，document 里的选中、拖动、改尺寸，都靠鼠标完成。用不了鼠标的人在这里做不了视觉创作，这跟读屏是同一个道理。所以：

| 项 | 做不做 |
|---|---|
| 鼠标操作 | **每个操作都先为鼠标设计**，鼠标走得通、走得顺是底线 |
| 键盘快捷键（撤销、删除、复制、缩放等） | **做**。它让创作者比用鼠标更快，快捷键必须 mac 和 Windows 两套 |
| 只为「键盘也能够到」而加的键盘路径（Tab 到某个按钮、按 Enter 打开某个弹层、给鼠标操作配一套键盘替代流程） | **不做**，不计入缺陷，不记待办 |

判定题：**这个按键让创作者比用鼠标更快吗？** 是 → 做；否 → 不做。

## 这条边界按「谁受益」划，不按「能不能操作」划

无障碍不是一件事，是一堆互相独立的条目。[WCAG 2.1](https://www.w3.org/TR/WCAG21/) 按「可感知 / 可操作 / 可理解 / 健壮」分它们，但那个分法对「我们做不做」没有指导意义。我们按**用鼠标创作的人受不受益**划。

## 先把两件事分开：Viewer 的「看和听」，跟读屏没关系

这两个词容易混，混了就会把正常的产品功能当成无障碍议题：

| | 是什么 | 承诺 |
|---|---|---|
| **Viewer（只读用户）看和听** | **权限**概念。`ProjectRole` 三档 `owner` / `editor` / `viewer`，viewer 不能编辑或修改内容，但打开项目就能看画布上已有的图和视频、听已有的音频（走 `MediaPlayer`，跟角色无关）、读文本 | **承诺内**，这是正常的产品功能 |
| **读屏** | **辅助技术**概念。让读屏软件把界面元素念出来 | **不承诺**，见下 |

Viewer 是用眼睛看、用耳朵听我们播放出来的内容；读屏是让软件替他念屏幕。**下面说的「不支持」只指后者。**

## 双受益的：本来就是前端质量，照常做

下面这些**不挂在「无障碍」名目下讨论要不要做** —— 它们是前端工业级标准的一部分，做不到就是质量不达标：

| 项 | 为什么它不只服务障碍用户 |
|---|---|
| 提高创作效率的快捷键 | 创作者用它比用鼠标快 |
| 键盘落到的地方焦点可见（输入框、快捷键作用的对象） | 正在打字或用快捷键的人要知道自己在哪 |
| 视觉可读（对比度、字号、不靠颜色单独传达信息） | 暗光环境、老花、劣质屏幕都吃这个 |
| 错误可懂（说清哪儿错了、怎么修） | 所有人 |
| 语义 HTML（用 `<button>` 不用 `<div onclick>`） | 浏览器默认行为、快捷键、右键菜单全靠它 |

**「不承诺读屏创作」不是砍这五项的理由。** 看到本文就去删快捷键或焦点样式，是读错了。

## 单受益的：读屏一律不支持

只有读屏用户受益的那一类，**全部在承诺之外**：

| 项 | 承诺到哪 |
|---|---|
| 读屏播报（`aria-label` / `aria-live` / 图片 `alt`） | **不承诺**，任何路径都不承诺 |
| 读屏驱动的完整操作流 | **不承诺**。生成、上传、节点编辑、连线、协作编辑，不保证读屏用户能独立完成 |

**为什么这么定**：breatic 做的是视觉和听觉内容的创作。用户有视觉障碍时，我们没有办法让他在这里创作 —— 这是对我们自己承诺范围的声明，不是对任何人能力的判断。

**产品设计里想到的、审查里咬出来的，任何需要读屏支持才成立的需求，一律按承诺外处理**：不做适配、不计入缺陷、不记待办。

## 判定题，只有一层

**这条投入进去，用鼠标创作的人受益吗？**

- 受益（看得更清楚 / 错误看得懂 / 快捷键让他更快）→ **归前端工业级质量，照常做**。不要拿「无障碍要不要做」当理由跳过。
- 只有读屏用户受益，或者只是让键盘也能够到某个鼠标已经能用的东西 → **不做**，也不当缺陷修。

## 三条具体规则

| # | 规则 |
|---|---|
| 1 | **读屏适配在任何路径上都不承诺**。不是技术上拦住谁，是读屏这条路径出问题不计入缺陷。**Viewer 用眼睛看、用耳朵听已有内容照常工作**，那是权限功能、不在这条之内 |
| 2 | **这一条免除读屏适配和只为键盘可达而加的路径**。快捷键、键盘落到处的焦点可见、对比度、错误提示照上面「双受益的」一节的标准做，一项都不减 |
| 3 | **不为读屏单独建机制**：不新增只服务读屏的 live region、朗读顺序编排、朗读专用的替代流程。已有的 `aria-*` 属性留着不动，它们同时服务测试选择器和语义 HTML |

## 对外怎么说

如实说，做到的和不做的都讲清楚：**支持以查看者身份使用**（看已有的图和视频、听已有的音频、读文本），快捷键、对比度照工业级标准做；**不支持读屏，也不提供完整的纯键盘操作**。

**不要在任何对外材料里声称符合 WCAG 2.1 AA 或 EN 301 549** —— 那两份标准包含大量我们明确不做的准则，声称符合就是虚假陈述。可以如实描述做到的具体项（快捷键、对比度等），不要用标准名做背书。

## 法规位置

[欧盟《无障碍法案》（EAA）](https://www.levelaccess.com/compliance-overview/european-accessibility-act-eaa/)2025-06-28 已生效，覆盖任何向欧盟消费者提供覆盖范围内服务的经营者，**不看公司注册地**。技术要求经由 EN 301 549 映射到 WCAG 2.1 AA（WCAG 2.2 尚未并入协调标准）。

**微型企业豁免**：员工少于 10 人**且**年营业额或资产负债表总额不超过 200 万欧元。注意两点：这项豁免**只覆盖服务、不覆盖产品**（我们是 SaaS 服务，适用）；**一旦超过阈值即刻失效，没有宽限期**。

**我们目前落在豁免范围内，本文的边界是在豁免前提下定的。** 接近或超过阈值时，这份文档必须重新拿给决策人审，不能默认沿用。

## 业界位置

Figma 在 [2025-10-14](https://www.figma.com/blog/introducing-screenreader-and-accessibility-features/) 发布了一批无障碍能力，其中画布对象已可被读屏访问、读屏会播报对象的类型与名称与状态，并配套了[纯键盘的画布导航与选取](https://www.figma.com/blog/introducing-keyboard-accessibility-features/)；[FigJam 也上了读屏支持](https://www.figma.com/blog/announcing-figjam-screen-reader-support/)。

所以「画布无障碍做不到」这个说法不成立 —— 头部厂商已经做到了。**我们不做是资源与优先级的选择，不是技术不可行**，对内对外都照这个事实表述。
