- [x] **等答复的请求统一到一个落地页(#25, 2026-08-03)**:五个流(studio 邀请 · project 邀请 · studio 转让 · project 转让 · 角色升级)各有一条 `share_token`,邮件 / 铃铛 / 发起人可复制的链接三条通道带同一个 token 到同一个 `/decision?token=`,一套 `GET /decisions/:token` + `POST /decisions/respond` 答五种请求。**「链接失效」这一句话原本压着四件事**(已答过 / 超时 / 被撤回 / token 是假的),现在各说各的,另加「关联内容已删」和「你已经在里面了」。token 是路牌不是钥匙 —— 闸门是登录 + 收件人校验,链接本身永不失效,过期的是请求。配套:两个互为镜像的旧落地页与其 API 删净;铃铛不再内联决策、只指路,没有 token 就不画按钮;角色升级补上它一直缺的邮件通路。**落地页上「你已经在里面了」的判据是角色不是行** —— 看的是收件人当前角色有没有到邀请要给的那一级,否则光是打开过那个 project(会当场把人物化成 viewer)就会让一条待答的 editor 邀请永久卡死。**这条只管落地页那一问**:发邀请那一刻问的是另一件事(这个人在外面吗),它按「成员表里有没有这一行」判是对的 —— 「邀请」的前提就是对方在外面,在里面就该直接告诉他已经是成员、让他走成员列表改角色
- [x] **选择这件事本身:可见的内容都能选中,选中之后操作有效(#111, 2026-08-17)**:document 的文档标题和正文住在同一个 ProseMirror 文档里(content 规则 `title block*`),「全选」和「拖选」的默认实现都会把文档的名字卷进选区 —— 一次改写落在名字上是撤销也救不回的破坏。这个切片把「选区永不跨越标题和正文」立成一条规则,一处回答:① **Ctrl+A 一档按侧**:光标在正文选整个正文、在标题选标题,判「在哪一侧」看位置区间不看父节点类型(整块被 Cmd+点击选中时两侧的父节点都是文档,分不开);② **拖选夹止**:从正文往上拖进标题,选区停在正文起点,反方向同样;③ **全选后说「这片不要了」统一收敛**(删除 / 剪切 / 打字 / 回车 / 输入法),挂在 `appendTransaction` 上按 step 形状判,不拦按键 —— 删除键有 5 到 11 个绑定,拦不全;**输入法是唯一「动作跨多个事件才完成」的入口**,组字期间不动手、`compositionend` 后两跳微任务再收敛(让编辑器自己的延迟冲刷先落地),远程协作者动了正文才作废收敛、只改标题不作废;④ **跨两个列表项按回车不再抛异常**:tiptap 自带的 `splitBlock` 用删之前的文档回答「能不能分」、在删之后的文档上动手(上游 #7734 开着),换成官方 `prosemirror-commands` 的实现,一条反向测试跑着 stock 版本 —— 上游修好那天它变红,就是删我们替换的信号;⑤ **Cmd+点击选中的块有可见选中框**:选中一直是真的,但 ProseMirror 把这个样式发在 tiptap 不加载的样式表里,补上(与画布节点选中同一个 token)。三轮实现对抗,其中输入法上屏残留组字键(`hao好`)由 user 真实输入法测出、对抗者探针又咬出远程编辑落在组字窗口会被收敛压平,两个方向各有测试钉住
- [x] **跑着不同版本的人一起编辑,谁也不破坏谁(#105, 2026-08-13)**:document Space 的内容存成 Yjs 片段,片段里的元素名**就是**编辑器的节点名,而这份「认得哪些名字」的清单编译在前端 JavaScript 里 —— 所以一个标签页一直没关的人跑的是旧清单,他看不懂新内容,而 y-tiptap 对看不懂的东西的处置是**从共享文档里删掉它**:别人写的段落对所有人消失,没有任何报错。**这个切片治的根因是「存储格式和编辑器的清单是同一个东西」**,分三样各管一件事。① **兜底类型 + y-tiptap 补丁**:收到不认识的东西时包起来而不是删掉。补丁的判据前移到构造之前、只认「这个名字不在清单里」——放在 catch 里会连上游的自愈一起接管(两个**同版本**的人各删掉同一个引用块里的一段,合并出的空引用块也走那个 catch,而删掉它正是 y-tiptap 在自愈)。兜底分块级和行内两种,因为**不认识的行内元素在文档加载时就被删掉、不需要任何编辑**,拦截根本来不及。② **服务器把这一版的清单写进 project meta**:清单和一个**从清单算出来的版本号**一起发布 —— 客户端比的是那个版本号,而它是两张清单的摘要,所以「改了清单忘了改版本号」造不出来(手写的数字会有这个问题:忘了改则检查照常通过而保护已经没了,还没有任何报错)。清单里带每个节点和标记的**属性名**,因为「给双方都认识的节点加一个属性」不会触发兜底,这个比较是唯一逮得到它的东西。跟着一起发的还有一个**人写的发布时刻**(UTC),面板拿它说「新版本发布于什么时候」—— 只有人知道一次发版是什么时候,机器算不出来;它不进版本号,所以改对一个日期不会把任何人拦住。清单、版本号和发布时刻都住在 `@breatic/shared` 的一个常量里,前端和 collab import 同一个符号。③ **拦截**:自己那份跟服务器发布的不一样(判「一样不一样」而不是「谁新谁旧」,回滚方向同样成立),或者这份文档里有解析不了的内容 —— 任一成立就不再打开这个 document Space,整块换成一条消息:说清现状、说清刷新那一条真实的代价(正在进行的上传会中断)、给一颗刷新按钮。**撤销和重做记录不在里面** —— 拦截成立那一刻编辑器已经被销毁、撤销栈跟着它一起没了,那是已经付掉的,不是刷新的代价。**编辑器是被销毁的,不是被盖住** —— 半透明的一层只答鼠标,焦点还在 contenteditable 里、键盘照打;真机实测拦截时 `contenteditable` 和 `.ProseMirror` 各 0 个。而销毁也不能换成「设成只读」:实测 `setEditable(false)` 会把本地补出来的空壳写回共享文档,并让跑着新版本的人抛 `RangeError`。**这是承诺外的收场方式** —— 说清楚、把选择权交给用户,不替他判断刷新管不管用,所以消息只有一个形态、没有任何分支。

  **列表按最近使用倒序分页**，游标是 `(updated_at, id)` 两列而不是 offset —— 这个顺序会随读者说话而动，offset 会漏行也会重复。**每次打开抽屉都重新拿第一页**：我们支持多端同时登录，服务器那份随时可能被另一端改掉，打开抽屉就是跟服务器对齐的那个时机；抽屉的用法本身也支持这一点，打开、找到、关掉，下次是重新开始找。手上那份列表在重取期间不清空（读者看到的是上次那份立刻在那儿、几百毫秒后被换掉），这跟 [RFC 5861](https://httpwg.org/specs/rfc5861.html) 的 stale-while-revalidate 和 [TanStack Query](https://tanstack.com/query/latest/docs/framework/react/guides/caching) 的默认行为是同一套。

  **一条被判定为不成立、因而没有修的时序**：复制先读出源、再等 studio 行锁，等待期间源被删掉的话副本照样产生。查了业界才确认这不该修——TOCTOU 这个模式遍布每一层，把它当缺陷的前提是**说得出被破坏的不变量**，而这里一条都说不出（副本是独立 project，不挂在源上；数量仍受限）。这正是快照语义。那四处「往 project 里加东西」的地方之所以锁源，是因为不锁会留下挂在死项目上的孤儿行——那个理由在这里不成立。
  **六个变异逐个验过**，其中两个是对抗关逼出来的：把 `>=` 改成 `>`、删掉行锁、复制路径跳过闸门、档位改从操作者取、文案不传参数、**文案把数字写死**。最后一个尤其值得记：原来那两条文案用例都跑在 base 档、上限正好是 10，所以 `{ limit: 10 }` 写死之后它们照样绿——补了一条 pro 档（100）的用例才形成能分辨的一对。

- [x] **每份文档同时能有几条可写连接，按档位限制（#88）**：会员六块里的第四块。上限从 `config/collab.yaml` 里写死的 100 换成拥有这个 project 的 studio 当前 admin 的档位，**满了的连接降为只读而不是被拒**——把人挡在门外和让人进来看着，是两种产品；后者才是这一层该有的样子。

  **数的是连接，而且只数可写的那些**。按人算，一个账号被任意多人共用只记一个，上限失去意义；把只读连接也算进去，上限 2 的文档来两个 viewer 就没人能编辑了，而他们一个字都不会写。取不到上限（project 不存在、studio 没有 admin、档位值不在枚举里、配置文件坏了）一律按满处理走降级，因为算不出上限时放行等于没有上限。

  **服务端把三个原因压成同一个只读标志发下来，而 wire 上没有位置放原因**：这份文档是 meta、这个人是 viewer、这份文档满了，客户端收到的是同一个布尔。所以前端要回答的不是「服务端说不行了吗」，而是「**这个人的编辑是不是被拿走了**」，做法是把另外两个原因从它已知的信息里排除掉：角色由 Space 外壳传进来、meta 由构造排除、被拒由 `authFailed` 分开。**这个判断第一版放错了层**——放在只拿得到连接状态的那一层，然后在注释里写「角色故意不掺进去，调用方自己加」，而唯一的调用方也是同一个人写的、没加，于是每个 viewer 打开任何一个 Space 都会读到一条说这个 Space 已满的常驻提示。教训是：**把一个必错的默认值留在那儿等人来补，就等于没做判断**。

  **提示住在 Space 内部而不是页面顶栏**，因为只读是**单份文档**的属性——画布满了、旁边的文档 Space 有位置，是完全正常的情形，一条飘在页面角落的提示没法说清它在讲哪一个。形态是常驻胶囊不是 toast：toast 四秒后自己走人，而这是一个一直成立到有人退出或重连的**状态**，错过那四秒的人只能靠「我的编辑怎么没了」自己发现。

  **前端把只读兑现到每个写入口（上传、生成、编辑）不在这一块**，单独排期；那意味着一个被降只读的编辑者今天仍点得动上传和生成，而它们走 HTTP 不走协作通道。

  **六轮对抗，最后两轮零承诺内类**。最重的两条都不是逻辑错，是**没被测住**：核心规则「只读连接不占席位」在服务端可以被静默还原，476 条 collab 测试全绿（测的是那个纯函数，不是调用它的那一行）；前端三个判据里只有一个有测试，收紧、放宽、把两个 id 对调，三个变异各自让全套测试保持绿。**十三次变异逐个验过**，每条都撤回并确认工作树干净。附带一条方法上的记录：对抗报回来的「放宽判据后 3690 条全绿」，按它说的做同一个变异跑全量，红了 1 条——它指出的缺口是真的，给的证据是假的。

- [x] **Studio 成员数和 Project 协作者数按档位限制（#87）**：会员六块里的第三块，两个上限一起接上，取值都来自该 studio 当前 admin 的档位（project 那个取的是它所在 studio 的 admin，不是它自己的 owner）。**每个上限有两个检查点，而它们不是一种东西**：发起邀请那个在事务外，是给邀请方的早提示，让人在邮件发出去之前就知道没位置了；接受邀请那个才是闸门，因为从发出到接受之间名额可能被别人占掉。
  **根因我一开始判错了，是 Gate 1 纠正的**。我写的是「两个计数函数写死了全局连接、不接事务句柄」，结论是光加行锁没用。对抗者跑了对照实验：有行锁时，排在锁后面的事务即使从连接池另取一条连接去数，那也是一条新语句、取新快照，看得见前一个已提交的行，数出来正好触发拒绝；去掉行锁才两边都数到旧值。**更硬的证据是我自己在块二写的那句 docstring 就是相反的** —— 它明写传句柄「不是为了正确性」，是为了别在持着一条连接时再去池里要第二条。真正的缺陷是两个 confirm 的事务里一把 `FOR UPDATE` 都没有。这条区别决定验证对着谁做：变异要拿掉的是锁，拿掉句柄而留着锁，行为不变、测试照样绿。
  **那把锁必须在接受邀请的 CAS 之前取，这不是偏好**。`deleteProject` 先锁 `projects`、再改它的邀请表；接受邀请的 CAS 本身就是一条改邀请表的语句。两者顺序相反就构成环，PostgreSQL 检测到会中止一方抛 `40P01`，落到用户那里是 500 —— 这个环在改之前**真实存在于发起邀请那条路径上**，集成测试先复现了它（`40P01`，被中止的是发起邀请那一方）才改的。studio 那一侧今天没有对手：**studio 删除还没做**（#26），那一侧取同样的顺序是为了让 #26 落地时不必回头找这条路径。所以要先用一次不加锁的读拿到实体 id（那一列不可变，谁赢得这条邀请仍由 CAS 决定），再锁，再 CAS。project 那把锁顺带堵上了一个既有缺口——项目已被删仍能接受邀请、留下一条挂在死项目上的成员行，`deleteProject` 的级联扫邀请表正是为了防它；studio 那侧的孪生缺口一并修掉，两者要么一起修要么一起留，不能各给一套理由。
  **两条文案拆成了四条**。原来发起和接受共用一个 key，而读到它的是两拨人：接受邀请的人既不持有那个档位、也没法把它调高，跟他说「升级可以增加」是一条他执行不了的指令，何况被拒之后邀请回滚成待处理、铃铛还挂着，他可以反复点、反复读到同一句。现在发起侧带这一档的真实数字加升级路径，接受侧告诉他名额满了、去找能腾位置的人。
  **口径两层不同，这是刻意的**：studio 数全部成员含 admin 本人（席位含管理员是通行做法），project 只数显式邀请进来的，owner 和开放基线自动物化的 viewer 都不计——把后者算进去，大 studio 里任何 project 一开就满。这个口径今天有个缺口：能把不计数的行变成有写权限成员的路径有三条（成员页改角色、角色升级申请通过、项目转让把原 owner 降成 editor），全都不碰 `added_by`。它不在这一块修，因为产生那类行的规则本身正要被废掉（所有 project 都可见、进入改成申请加入由 Owner 审批），补在一条即将消失的规则上等于白补。
  **六个既有测试套件要跟着改，其中三个还删了用例**（第六个是 `membership-tier-lookup`，它的 docstring 里写着「还剩几个上限没接」，本块接上两个之后那句话就错了）。它们把 team studio 的 admin 建在 base 档上，而 base 允许一个 studio 成员——admin 自己那个座位——于是那些套件里每一条邀请都因为没位置被拒，而不是因为它们各自要测的原因。（base 账号**确实**可能管着 team studio：转让和降级都不校验档位。它只是一到那儿就谁也邀请不了。）另有一个套件的 studio 没有 admin 行，而协作者上限正是经那一行读出来的。**三个套件里关于旧上限的 9 条用例是删掉的**（两个邀请套件各 3 条，加上 `limits.test.ts` 里 3 条——两个 getter 的断言，和「两个 cap 的默认值都是 100」那条）：它们验的是「上限来自 `limits.yaml`」，那个机制连同那两个配置项一起没了。**`limits.test.ts` 里另有 3 条是改的不是删的**：「非正数被拒」和「接受显式正整数」两条都还在，只是校验对象从已删掉的 `studio_member_cap` / `project_collaborator_cap` 换成了 `activity_feed_page_max`（前者连 `it` 的标题都改了，后者标题没动、只换了断言里的键）；「每个 getter 只读自己那个键」那条也还在，只是摘掉了关于这两个 cap 的两行断言。这个数第一次写成了 6、第二次写成了 10，两次都是数 diff 的减号行——而改名会在减号侧留下一行看着像删除的痕迹，所以这次数的是文件里的 `it` 块。同样的行为在新套件里覆盖得更全（两个检查点、两拨读者各自的文案、并发、实体已删），其中「拒绝之后邀请回滚为待处理」这一条是逐条比对后补回去的。

- [x] **会员档位机制打通，第一层配额按档位生效（#16，PR #440）**：会员这块拆成六块交付的第一块。起点是 `studio.service.ts` 里一个写死的 `TEAM_STUDIO_LIMIT = 50` —— 一刀切，而档位决议早就定了这一层按档位分 0 / 1 / 3；拒绝文案还把「50」写进了五种语言的句子里，那句话在常量时代是对的，变成按档位的那一刻对每一档都是错的。**这一块打通的是整条链路**：`users` 上一列档位、`config/membership.yaml` 里四档各六个上限、两条从 id 到档位的查询、以及一层限制真的走完全程。后面五块各自往这条已通的链路上挂一个校验点，不必再动机制。
  **档位归属看当前 admin，不看创建者**：可建 team studio 数看账号自己的档位，其余四层加存储一律看该 studio **当前 admin** 的档位。所以查询读的是 `studio_members.role`，永远不读那个不可变的 `created_by_user_id` —— studio 转让之后，新 admin 的档位立刻接管它的全部上限。
  **配置里没有「无限制」这个概念**：每个值都是普通的非负整数上限，判定一律 `count >= limit`，代码里没有任何针对特定值的分支。想表达不设限就填一个够不着的数。所以 `base.team_studios: 0` 就是真值零——那一档确实一个团队 studio 都不能建，而同一个比较自然地拒绝它。
  **两轮对抗咬出四个真洞**：新账号的档位字段被读进配置、被校验、被冻进内存，然后零调用方（自托管装完每个账号都落最窄那档，一个团队 studio 都建不了，而拒绝文案叫他去升级）；并发下上限拦不住（实测上限 1 的档位，三个同时到达的请求成功了两个——这个竞争在常量时代就有，只是那时超一个无所谓，现在超的是用户花钱买的东西）；档位列是裸 `varchar` 没有 CHECK，手写 UPDATE 打错字会变成一句没有上下文的 TypeError；以及最宽那一档的上限没有任何测试钉住，把它改成 0 时 52 条测试全绿。
  **还撤掉了一块本不该加的东西**：我给配置预热加了条 ESLint 规则守着它别被删，两轮对抗分别咬出「形状不对」和「防不住它自己声称要防的回归」。整块撤掉，理由不是它有洞——是「有人可能删掉它」这个理由对仓里每一行代码都成立，因此不能用来把某一行挑出来特殊对待；而且仓里有十来个配置文件、好几个惰性加载器，只给其中一个加守卫，说明这个理由自己都站不住。真要做就做覆盖全部配置的统一检测。

- [x] **后端的错误按用户选的语言回话（#64 + #60）**：起点是三个接口把校验失败报成 500，查下去发现「用户看到自己选的语言」这件事整条链路都没接上。**校验这一半**：47 处入口分两种坏法 —— 其中 44 处直接挂 `@hono/zod-validator`，失败时把 zod 的报告整个丢回去（`error.message` 是一串 JSON，里面还嵌着完整的邮箱正则），前端拿到的既不是我们的格式也不是任何一种语言；另外 3 处在 `studios.ts` 里连库都没走、自己 `schema.parse(await c.req.json())`，抛出来的裸 `ZodError` 不是 `AppError`、落进 500 那条分支，正是起点那三个接口。现在 47 处统一走 `packages/server/src/middleware/validate.ts` 的 `validate(target, schema)`，失败在 hook 里抛 `ValidationError`、经统一出口成 `{error:{code,message}}`。**状态码按「读得出来没有」分**：字段读出来了但不合法是 422（跟同文件里手写校验的既有做法一致）；请求体读不出来是 400（RFC 9110 §15.5.1，也是 hono 自己在 `HTTPException` 上带的那个码），**但只在请求声明了 JSON 的 Content-Type 时** —— hono 只对那个 Content-Type 尝试解析，尝试失败才抛；同一个坏 body 不带那个头就压根不解析，schema 对着 `{}` 跑，仍然是 422。31 条既有 `toBe(400)` 断言逐条判过改与不改。**出口按「谁造成的」判，不按异常类型判**——原先想按 `ZodError` / `SyntaxError` 认，实测否掉：我们自己的 config yaml 也是在请求内惰性解析的，按类型认会把运维的 typo 当成用户输入错误回给用户、还把日志整个丢掉；现在只认 `AppError`（我们自己抛的）和 `HTTPException`（hono 抛的、body 读不出来），其余一律 500 + `logger.error`。**语言这一半**：后端每一句客户端读得到的错误都经 `t()`（`packages/{server,domain,core}/src` 共 158 处构造、零裸字面量），五本目录各增 26 个 `server.*` 键；前端 axios 拦截器和 `sse.ts` 都带上**用户选的**语言而不是浏览器的。**两道新守卫**：`breatic/no-raw-body-parse` 盯路由自己解析请求体（漏洞的形状是「绕过了库」不是「用错了库」，盯 import 看不见这个差别）、`breatic/no-untranslated-error-message` 盯这一族错误的消息参数写字面量。**真浏览器验的是那个差别本身**：浏览器语言 `zh-CN`、界面选日文，同一个用户同一个接口同一个错误密码，走拦截器拿到「メールアドレスまたはパスワードが正しくありません」，用原生 `fetch` 绕过拦截器拿到「邮箱或密码错误」——没有这个拦截器，界面是日文而错误是中文。五轮对抗。

| 4 | agent 的联网工具：`web_fetch`（经 `safe-fetch.ts`）+ `web_search` | 已接入（#400）| 这两个工具此前各自裸 `fetch` 且**零重试**，一次网络抖动就是一次工具失败，也是整条线的起因。两处均声明 `replaySafe: true`（都是纯读，一次投递的唯一效果就是那个响应），原有 30 秒 / 10 秒原样搬进 `timeoutMs`。**同批给 SSRF 守卫补了第一份自动化测试**——这个安全控制此前零覆盖，其中 IPv6 字面量走的是跟 IPv4 不同的那条分支（`URL.hostname` 保留方括号，`ipaddr.isValid("[::1]")` 因此是 false），本批之前没有任何测试保护它。**两个语义变化**：`timeoutMs` 管一次投递而不是一跳（一跳可能被投递多次，每次各拿全额，所以它不再是一跳的上界）；读响应正文这一步不再受它管（传输层在交出响应前就把定时器清了），归「工具级超时」统一处理，不在本批内改 |
| 5 | 加守卫封住裸 `fetch` + 同步文档 | 已接入（#403）| 新规则 `breatic/no-naked-fetch` 按**作用域解析**判「这个名字指向平台那个 `fetch` 吗」，不按调用形状匹配。判据只有一条：**这个标识符解析到平台的 `fetch`，而且它在值位置** —— 所以「不调用只传递」的写法（赋给变量、当简写属性、当实参）一样抓，三个载体（`globalThis` / `window` / `self`）的点号和计算成员两种拼法一样抓；局部同名参数不抓（它压根不是那个 `fetch`），纯类型位置也不抓（`typeof fetch` 编译后就没了、发不出请求，判据抄 ESLint 自己的 `no-restricted-globals`）。**具体几种写法不写在这儿** —— 规则测试文件的用例列表就是那份清单，写个数字在文档里只会过期。**两处声明**：根配置管 6 个后端包，`packages/web/eslint.config.mts` 管 web，因为从 web 启动的 ESLint 读不到根配置。同批删掉三个零消费方的配置键（`http_max_retries` / `http_retry_base_delay` / `download.*`，共六个位置），并把 core 那份逐字节相同的退避副本折进 `shared/backoff.ts` —— core 只留 BullMQ 那个 1 起头转 0 起头的换算 |

**给碰到外部 HTTP 的人**：新写的外部请求直接用 `httpRequest`，别再自己写重试循环 —— 这条线的起因正是同一个判据在三处写了三遍、给出三个不同答案。
