# Accessibility boundary

本文定的是**我们承诺什么、不承诺什么**，不是当前实现的证明。现状跟这条边界之间的差距按普通缺陷追踪。

## 这条边界按「谁受益」划，不按「能不能操作」划

无障碍不是一件事，是一堆互相独立的条目。[WCAG 2.1](https://www.w3.org/TR/WCAG21/) 按「可感知 / 可操作 / 可理解 / 健壮」分它们，但那个分法对「我们做不做」没有指导意义 —— **键盘可达（属于「可操作」）对所有重度用户都有价值，而读屏播报（属于「可感知」）只有读屏用户听得到**。按「能不能操作」划线，会把这两样正好切反：砍掉所有人都受益的，留下只有一部分人受益的。

所以我们按**谁受益**划。

## 双受益的：本来就是前端质量，照常做

下面这些**不挂在「无障碍」名目下讨论要不要做** —— 它们是前端工业级标准的一部分，做不到就是质量不达标：

| 项 | 为什么它不只服务障碍用户 |
|---|---|
| 键盘可达（Tab 能到、Enter 能按、快捷键齐全） | 创作工具的重度用户几乎全靠键盘。快捷键必须 mac 和 Windows 两套 |
| 焦点可见 | 键盘用户不知道自己在哪就没法工作 |
| 视觉可读（对比度、字号、不靠颜色单独传达信息） | 暗光环境、老花、劣质屏幕都吃这个 |
| 错误可懂（说清哪儿错了、怎么修） | 所有人 |
| 语义 HTML（用 `<button>` 不用 `<div onclick>`） | 浏览器默认行为、快捷键、右键菜单全靠它 |

**「不承诺读屏创作」不是砍这五项的理由。** 看到本文就去删键盘支持或焦点样式，是读错了。

## 单受益的：承诺止于「查看已有内容」

下面这些只有读屏用户受益：

| 项 | 承诺到哪 |
|---|---|
| 读屏播报（`aria-label` / `aria-live` / 图片 `alt`） | **查看路径承诺**：项目列表、画布上已有内容、文本、音视频的存在与身份，读屏要能读到。**创作路径不承诺** |
| 读屏驱动的完整创作流 | **不承诺**。生成、上传、节点编辑、连线、协作编辑，不保证读屏用户能独立完成 |

**为什么这么定**：breatic 做的是视觉和听觉内容的创作。我们**不承诺**读屏驱动的创作路径可用 —— 这是对我们自己承诺范围的声明，不是对任何人能力的判断。

## 判定题，两层

**第一层：这条投入进去，除了读屏用户，还有别人受益吗？**

- 有（键盘用户 / 暗光下的人 / 所有人）→ **归前端工业级质量，照常做**。不要拿「无障碍要不要做」当理由跳过。
- 只有读屏用户受益 → 进第二层。

**第二层：它服务的是「看到 / 听到已有内容」，还是「做出新内容」？**

- 前者 → 承诺内，做不到是缺陷。
- 后者 → 不在承诺范围，不做适配、也不当缺陷修。

## 三条具体规则

| # | 规则 |
|---|---|
| 1 | **允许以 Viewer 身份参与**。查看项目、看画布已有内容、听音频、读文本，读屏要能读到 |
| 2 | **即使被授予 Editor 权限，也不承诺读屏驱动的编辑可用**。不是技术上拦住谁，是这条路径出问题不计入缺陷 |
| 3 | **生产和生成类功能的读屏适配不承诺**：生成面板、mini-tool、上传、节点编辑、画布操作、协作编辑。**这一条只免除读屏适配** —— 这些功能的键盘可达、焦点可见、错误提示照上面第二节的标准做 |

## 对外怎么说

如实说，不假装做到：支持以查看者身份使用，不承诺无障碍环境下的内容创作。

**不要在任何对外材料里声称符合 WCAG 2.1 AA 或 EN 301 549** —— 那两份标准包含大量我们明确不做的准则，声称符合就是虚假陈述。可以如实描述做到的具体项（键盘可达、对比度等），不要用标准名做背书。

## 法规位置

[欧盟《无障碍法案》（EAA）](https://www.levelaccess.com/compliance-overview/european-accessibility-act-eaa/)2025-06-28 已生效，覆盖任何向欧盟消费者提供覆盖范围内服务的经营者，**不看公司注册地**。技术要求经由 EN 301 549 映射到 WCAG 2.1 AA（WCAG 2.2 尚未并入协调标准）。

**微型企业豁免**：员工少于 10 人**且**年营业额或资产负债表总额不超过 200 万欧元。注意两点：这项豁免**只覆盖服务、不覆盖产品**（我们是 SaaS 服务，适用）；**一旦超过阈值即刻失效，没有宽限期**。

**我们目前落在豁免范围内，本文的边界是在豁免前提下定的。** 接近或超过阈值时，这份文档必须重新拿给决策人审，不能默认沿用。

## 业界位置

Figma 在 [2025-10-14](https://www.figma.com/blog/introducing-screenreader-and-accessibility-features/) 发布了一批无障碍能力，其中画布对象已可被读屏访问、读屏会播报对象的类型与名称与状态，并配套了[纯键盘的画布导航与选取](https://www.figma.com/blog/introducing-keyboard-accessibility-features/)；[FigJam 也上了读屏支持](https://www.figma.com/blog/announcing-figjam-screen-reader-support/)。

所以「画布无障碍做不到」这个说法不成立 —— 头部厂商已经做到了。**我们不做是资源与优先级的选择，不是技术不可行**，对内对外都照这个事实表述。
