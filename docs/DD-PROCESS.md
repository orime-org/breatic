# Due Diligence (DD) — 完整流程文档

> **本文是 DD 流程的完整参考**(详细模板 + 反例 + 衔接图)。 CLAUDE.md 中的 DD 章节是项目级 mandate(必读),本文是 dev 实际执行 DD 时的操作手册。

## 1. 什么算"重大决策"(任一即触发 DD)

触发条件都是**动手前就能 grep / 实证验证的客观信号**(不按"工作量周数 / 反悔代价"等时间度量估 —— 那对 AI 没有 anchor,且要等出问题才知道,属滞后判断)。任一命中即触发:

- **安全模型**(支付 / 鉴权 / 数据完整性 / AI tool call / 积分扣减 / Yjs 协作 / 凭据存储 / 外部网络 / 用户数据)
- **跨界**(跨 ≥ 2 package 接口 / 共享类型 / 全局状态 / 数据模型 / DB schema / 协议变更 / 关键 dep 增删/大版本升级)
- **已扩散**(merge 入 main / 已 push 给其他 CC 或 long-living branch / 已落 ADR 被下游引用 / 已发给用户)
- **架构 / 长期维护**(整体目录结构 / 公共 API / 跨服务边界 / 核心依赖)
- **状态机**(一个事实有 ≥ 2 种状态,且有 ≥ 2 条路径能改它 —— 面板 / 会话 / 任务 / 连接 / 上传 / 长跑作业的生命周期)

这 5 类正是"反悔代价大"的可观察前置信号:**已扩散** = 撤回要通知所有下游消费者 / PR / ADR;**跨界** = 回滚要协调多 package、可能 break 跨包接口;**安全模型** = 要恢复 invariant + 重测整套安全 path;**架构 / 长期维护** = touch 公共 API / 跨服务边界、影响 codebase 长期方向;**状态机** = 路径数随动作数按平方增长,补一条漏的转移往往要动所有写入点,而漏掉的那条只有运行时才暴露。

### Breatic 高频场景示例

以下是上述触发的**具体化示例**,不是新增 mandate:

| 高频场景 | 对应触发 |
|---|---|
| AIGC provider 选型(image / video / audio / 3d / tts / understand 模型路由) | 架构/长期维护 + 跨界 |
| Agent / Skill 定义变更(system prompt / tools 列表) | 安全模型(prompt injection)+ 架构/长期维护 |
| 核心架构变更(两层记忆 / Turn 压缩 / Yjs 结构 / Redis Streams) | 架构/长期维护 + 跨界 |
| 积分 / 计费机制(pricing / Stripe webhook / 扣费幂等) | 安全模型 + 已扩散 |
| 部署形态变更(Docker / nginx / CI 流水线) | 架构/长期维护 + 已扩散 |
| 全前端重写 / 长 living branch | 架构/长期维护 + 跨界 + 已扩散 |
| 面板 / 会话 / 上传 / 长跑作业的生命周期(加载态 · 就绪态 · 失败态 · 在飞请求 · 离场清理) | 状态机 |

## 2. 两类 DD

| 类型 | 适用 | 流程 |
|---|---|---|
| **A. 选型 DD**(5 步全套) | 多候选选择题(哪个库 / 架构 / 路径) | 第 3 节 |
| **B. 事实验证 DD**(轻量版) | "假设 X 成立吗" 类问题(hook 行为 / API schema / 协议字段填充率) | 第 4 节 |

## 3. 选型 DD 的 5 步流程

### Step 1 — 候选枚举

穷举所有可见候选,**包括但不限于**:

- `from scratch`(自己实现)
- vendor in(把第三方代码搬进 package)
- npm / pip / cargo depend(直接依赖)
- 第三方 API 调用
- 跨语言抄(借 Go / Rust 实现)
- 已有 breatic 内部代码可复用

**禁止**只列 2-3 个候选(假对比)。即使某些候选明显劣,也要列出+给筛选理由。

### Step 2 — 每候选尽调(5 维度)

对每个候选,从 5 个维度收集**可引用证据**:

| 维度 | 检查内容 | 证据形态 |
|---|---|---|
| **实测** | 能装能跑?核心 path 通? | demo test commit hash + 跑通日志 |
| **源码** | 体量(行数 / 文件数)/ 模块化 / 测试覆盖 / 依赖清单 | GitHub stats / `cloc` / `npm view` |
| **治理** | commit 频率 / issue 响应 / 维护者画像 / license | GitHub Insights / GitHub Pulse / SPDX |
| **安全** | 外部 HTTP / 用户数据上传 / 已知 CVE / 沙盒越狱 | Snyk / GitHub Security / npm audit |
| **上游跟进** | 协议变化时这个仓库的反应速度(如适用) | 历史 release note 时间分布 |

**禁止**填"印象 / 感觉",必须可追溯到具体证据。

### Step 3 — 对比矩阵

候选 × 维度 → 表格。每格 cell **必须填**:

- 实证数据(数字 / 状态)
- 引用 link(commit hash / GitHub link / log 路径 / Snyk advisory ID)

**禁止**留空 cell 或填"待补"。无证据就明确写"未找到 / 不确定",不要装作有数据。

### Step 4 — 推荐 + 理由

每条推荐理由**必须可追溯到矩阵某格证据**。

格式:

```
推荐:候选 X
理由:
1. <理由 A> — 证据:矩阵第 N 行 M 列
2. <理由 B> — 证据:...
3. ...
```

**禁止**单点论据(只引一格)。**禁止**总结性陈述(如"它 stateless 所以好",但 stateless 不是矩阵 cell)。

### Step 5 — 用户决定

- DD 报告 commit 入仓库前,**必须经过用户(maintainer)review + 显式拍板**
- 用户拍板时间 + 依据写入 DD 报告"用户决定"段
- 锁定到 CLAUDE.md / 其他相关 docs(如适用)

## 4. 事实验证 DD(针对"假设"而非"选型")

适用场景:"假设 X 成立吗"类问题(如:hook 行为 / API schema / 协议字段填充率 / 性能假设)。

### 流程

1. **假设清单** —— 列出 N 条具体假设(每条带 ID,如 H1 / H2)
2. **实测方法** —— 每条假设的实测脚本 / 命令 / 输入
3. **实测结果** —— 实际数据
4. **假设状态升级表** —— 每条假设标 ✅ 验证 / ❌ 推翻 / ⚠️ 部分

### 输出

仍归档到 `docs/dd/<YYYY-MM-DD>-<topic>-dd.md`,但**不需要候选枚举 / 对比矩阵**(不是选择题)。

## 5. 反 DD 模式(一律违规)

| 反 pattern | 表现 |
|---|---|
| **浅表决策** | 凭 star 数 / README / "感觉合适" / share 对话拍板 |
| **hearsay 升格** | 把 AI 对话(含 ChatGPT / Claude share)当 ground truth |
| **假对比** | 跳过候选枚举只列 2-3 个 |
| **单点论据** | 推荐时引用单一证据(如"它 stateless 所以好") |
| **治标补丁** | 提议"先用 X 后续再换"(违反 CLAUDE.md #5) |

## 6. DD 文档要求

### 保存位置

DD 报告**必须归档**(不进 git = 没真正 DD 完),具体位置由各团队约定:

| 文档类型 | 推荐位置 |
|---|---|
| 公开选型 DD(技术栈 / OSS 库 / 架构) | 团队工程文档目录(若公开则放公开 `docs/dd/`;若团队有私有工程仓则放私有仓) |
| 敏感选型 DD(vendor 关系 / 内部成本 / 安全模型) | **不入公开仓库** — 团队私有 channel(Notion / 内部 wiki / private repo) |
| 事实验证 DD | 同选型,文件名后缀 `-verify.md` |

**为什么模糊化路径**:DD 流程是通用工程纪律,具体归档目录是 breatic 团队的私有约定。OSS contributor 看到的 DD 流程是规则,具体路径在团队的 `CLAUDE.local.md` / 内部 wiki 里指定。

### 命名规范

- `<YYYY-MM-DD>-<topic>-dd.md`(选型)
- `<YYYY-MM-DD>-<topic>-verify.md`(事实验证)
- topic 用 lowercase + dash 分隔,描述精确(`yjs-collab-protocol-dd.md` 不是 `yjs-dd.md`)

### 强制要求

- **跟设计 doc / PR 一起 commit**(**不进 git = 没真正 DD 完**)
- **每个论断必须可追溯到具体证据**(commit hash / issue 链接 / log / 实测产物路径)
- DD 报告完成后,在相关 PR description 中 link 到 DD 报告
- audit role 在 PR review 时核查 DD 是否合规
- **命中「状态机」触发的,报告里必须有第 9 节那四张表,且转移表每格都填**(空格 = 设计没做完)

## 7. 违规成本

> 未做 DD 就动手 = **违反纪律 = 当场撤回**。
> 绕开 DD 的方案 = **治标补丁 = 对用户时间的犯罪**(用户耗费精力识别、拆穿、重提需求)。
> 发现自己写了未 DD 的方案 → 立即撤回、重做,**不许辩护、不许找理由、不许谈工作量**。

## 9. 状态机的转移文档(命中「状态机」触发时必填)

一个事实有 ≥ 2 种状态、且有 ≥ 2 条路径能改它,就要在 DD / 设计文档里交出下面的表。**先于实现代码存在** —— 它不是实现完了补的说明书,是实现的依据。

**先做 9.1 那一步:数清楚有几个这样的事实。** 一份数据从产生到用户看见,中途常常被好几处各自存一份、各自改一份 —— 每一处都是一个独立的事实,都要单独过一遍上面那道判据,命中的每一处各填一套 9.2 到 9.5。**只给其中一处填表,剩下几处就是没有设计。**

**为什么是硬要求**:动作数 N 增长时,「动作与动作之间怎么相处」的组合是 N² 级的。按一个动作一个函数写下去,每个函数各自决定改哪些状态,新加一个动作就凭空多出 N 组没人定义过的交互;它们不会在 typecheck 或单测里响,只会在运行时被用户或对抗一条一条撞出来,而每撞一条都得回头动所有写入点。**把表填满是唯一能一次性穷举这些组合的办法**,因为表格的空格子是看得见的,而代码里缺失的分支看不见。

### 9.1 先数清楚有几个事实要填表

顺着这份数据从产生到最终被人看见走一遍,每停一处就问:**这里是不是又存了一份、又有人能改它?** 是 → 它是一个独立的事实,单独过判据(几种状态 · 几条路径能改),命中就为它单独填 9.2 到 9.5。

| 停在哪 | 问什么 | 命中了怎么办 |
|---|---|---|
| 产生的那一处 | 谁写它、什么时候写 | 填一套表 |
| 中途每一处存了副本的地方 | 副本什么时候更新、什么时候跟源头不一致 | 各填一套表 |
| 最终决定屏幕上画成什么样的那一处 | 画法由哪几个输入决定、它们各自何时到达 | 填一套表 |

**不经过我们的代码的那几段不算**(网络传输 · 第三方库内部),它们没有我们能填的格子。

**代价是实测出来的(任务 #2004,画布协作在场)**:这份数据经过五段 —— 发布 · 传输 · 读取 · 镜像 · 渲染,除传输外四段都在我们自己的代码里,四段各自都有 ≥ 2 种状态和 ≥ 2 条路径能改。当时交出的是发布端那一段的表(四个状态乘二十个事件,每格都填)。实现对抗跑了五轮,十条承诺内问题里**六条落在没有表的那三段**:

| 段 | 条数 | 其中一条 |
|---|---|---|
| 渲染 | 4 | 标签行靠自量决定放几个名字,而 flexbox 在测量之前已把每个标签挤到装得下,`+N` 从不出现 |
| 读取 | 1 | 同一节点上几个人的先后由到达顺序决定,谁被折进 `+N` 是随机的 |
| 镜像 | 1 | 占用变化单独到达时跑了整个节点镜像,而镜像从共享文档取位置,正在拖的节点被打回原处 |

另外两条落在发布端那张表里 —— 表在,但事件全集少了两行(窗口失焦 · 容器尺寸变化)。剩下两条是表写了而实现漏做。

判定题:**我正要写的这个东西,从产生到上屏经过几处各自持有状态的地方?每一处我都单独判过、单独填过表吗?**

### 9.2 状态全集

| 状态 | 它是什么 | 此时用户看到 / 系统行为 |
|---|---|---|
| `idle` | 还没开始 | ... |
| `loading` | 请求在飞 | ... |
| `ready` | 拿到了 | ... |
| `failed` | 没拿到 | ... |

穷举的判据:**这一列的取值加起来,能不能覆盖这个事实的所有可能?** 说不出就是还有没命名的状态藏在别的变量里。

### 9.3 事件全集

| 事件 | 谁触发 | 带什么数据 |
|---|---|---|
| 用户点了 X | 用户 | ... |
| 响应回来了 | 网络 | ... |
| 响应失败了 | 网络 | ... |
| 超时 | 定时器 | ... |
| 离场 / 卸载 | 路由 | ... |

**容易漏的三类**:失败、超时、离场。它们不是用户动作,所以按「一个按钮一个函数」写代码时不会自然出现。

### 9.4 转移表(每格都填)

行是状态、列是事件,**每一格写「→ 新状态」加条件**;不可能发生的格子写「不可能」并说明凭什么不可能。

| | 用户点了 X | 响应回来了 | 响应失败了 | 离场 |
|---|---|---|---|---|
| `idle` | → `loading` | 不可能(没有请求在飞) | 不可能(同上) | → 清空 |
| `loading` | → `loading`(旧的作废,见 9.5 仲裁) | → `ready` | → `failed` | → 清空 |
| `ready` | → `loading` | 迟到的响应,丢弃 | 迟到的失败,丢弃 | → 清空 |
| `failed` | → `loading` | 不可能 | 不可能 | → 清空 |

**「不可能」也要给理由**。写不出理由的,说明它其实可能,只是还没想到怎么发生 —— 那一格就是待定义的路径,不是空白。

### 9.5 不变量与写入点

| 项 | 内容 |
|---|---|
| 不变量 | 任何时刻都成立的断言,例如「处于 `loading` 必然有至少一个请求在飞」「`failed` 必然带着一条失败原因」。**每条不变量对应一条测试**。 |
| 唯一写入点 | 每个状态由**哪一个函数**负责写。多条路径要改同一个状态时,它们一律调这个函数,而不是各写各的。 |
| 仲裁规则 | 多个动作并发时谁说了算。典型:后发起的作废先发起的、失败的那个要把决定权交还给还在飞的最新那个。**并发只写在这里,不散落在各个动作里**。 |

写入点这一行是最容易被跳过、也最贵的一行:同一个状态有四五处各自 `set`,任意两处之间的相处方式都得单独想一遍,而想漏的那对只有运行时才知道。

## 10. DD vs 普通设计的区别

| | 普通设计 | DD |
|---|---|---|
| **过程** | 你想了一下觉得 X 合理 → 写代码 | 穷举所有 X 替代品 → 用数据比较 → 给用户可质疑的推荐 → 用户拍板 → 才写代码 |
| **输出** | 代码 + commit message | DD 报告(可被审计 / 反驳) + 用户拍板 + 代码 |
| **本质** | 经验直觉 | **强迫自己跳出第一直觉,看见自己没看见的可能性** |

DD 的本质**不是流程仪式感**,而是**强迫看见自己没看见的可能性**。

如果你做 DD 后发现"哦原来还有这条路"或"哦那个候选其实更合适",DD 就成功了。如果做完后觉得"果然还是我最初想的那个" — 仍 OK,但要诚实问"我是真的对比了,还是只是 confirmation bias"。

## 11. DD → TDD 衔接

DD 锁定方案后,实施时走 TDD 节奏(详见 [CLAUDE.md "Test-Driven Development" 章节](../CLAUDE.md#test-driven-development-tdd--ai-coding-时代版))。本节描述 DD 与 TDD 的边界、衔接、AI 时代的反闭环约束。

### 衔接图

```
DD 锁定方案 → TDD 写代码(红 → 绿 → 蓝)→ 关键路径 100% + invariant 覆盖 → smoke / E2E ship 验证 → CI 强制 → commit
   ↑                                                                                    ↓
   └─── 实施中发现 DD 假设错 → 停下重做 DD ───────────────────────────────────────────────┘
        (不在错假设上打补丁,违反 #5)
```

> smoke / E2E ship 验证这一步(起真实 runtime 端到端跑)的操作规范见 [docs/TEST-MANDATE.md](./TEST-MANDATE.md)。

### DD vs TDD 边界

| 维度 | DD | TDD |
|---|---|---|
| **阶段** | 决策前 | 决策后实施 |
| **解决** | "做什么 / 选什么" | "实现是否正确" |
| **范围** | 对外部库 / 假设 / 跨包接口 | 对自己写的代码 |
| **节奏** | 候选枚举 / 尽调 / 矩阵 / 推荐 / 决定 | 红 → 绿 → 蓝 |

### 重叠场景

- **选型 DD 的"实测"维度** ≈ 迷你 TDD(候选库写一条 demo test 看核心 path 通)
- **事实验证 DD** 本身就有 TDD 节奏(声明假设 → 实测 → 看结果)
- **TDD 红色阶段写"会失败的测试"** = 半个事实验证 DD(用测试 codify 假设)

### AI 时代特别约束

业界共识(Anthropic / Kent Beck / case study)证实 AI coding 引入新风险,DD-TDD 衔接需注意:

1. **DD 假设错 → 立刻停 + 重做 DD** —— 实施中发现假设错,**禁止**在错假设上打 TDD 补丁(违反 #5)
2. **测试 cheat detection** —— TDD 阶段如果 AI 删 / 禁测试通过,警惕(Kent Beck 明确警告)
3. **测试 as draft mindset** —— AI 写的 TDD 测试是初稿,review 时显式审 invariant 是否覆盖真实约束
4. **Writer/Reviewer 强制分离** —— 一个 Claude session 不能同时定义 expected(spec)+ 写 test code + 写实现
   - Breatic 实践:audit 写 spec(`bugs/audit/round-N-found.md`),dev 写 test code,严格分离

### TDD 失败的处理

- TDD 中测试无论如何写不通 → 多半是 DD 假设错(spec 与现实不符)
- **不要**"修 test 让它过" 或 "调实现迎合 test" —— 都是补丁
- **正确做法**:回到 DD 阶段重审假设,可能要重开 DD(候选枚举 / 矩阵 / 重新拍板)

## 衔接到 audit 流程

audit role 对 DD 的核查机制:

- 任何 PR / commit 改动满足 DD 触发条件之一时,audit 必须核查 PR description 是否含 DD 报告引用
- 无 DD 报告 → 记入 BUGS.md 流程类条目
- audit 不替 dev 写 DD,只 catch 缺失
