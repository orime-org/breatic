# @breatic/shared — 包边界(MANDATORY)

> 项目级三层边界 + 进包判定题见根 [CLAUDE.md](../../CLAUDE.md#关键规范)。本文件只写本包的边界规矩,细节见 [docs/ARCHITECTURE.md](../../docs/ARCHITECTURE.md)。

## 角色
**web + 后端共用**的纯协议层:zod schema · 类型 · 常量 · 跨服务事件契约的数据格式 · **统一 HTTP 传输层**(`http/`)与退避原语(`backoff.ts`)。

## 统一 HTTP 传输层(`src/http/`,#36)

**这一层做七件事,没有第八件(user 2026-08-02 拍板六件 · 2026-08-10 拍板加第 7 件)**。这份清单同时是功能定义、验收标准和终止条件:

| 条 | 功能 |
|---|---|
| 1 | 发请求 —— 调用方给的地址和参数原样发出去 |
| 2 | 判断该不该重试 —— 协议语义(429/408/5xx 可重发,其他 4xx 不重发)+ 调用方声明的一个事实(重发会不会多花钱)+ 传输层自己判的一个(这个 body 物理上还能不能再发一遍) |
| 3 | 等多久 —— 服务器说了听服务器的,没说才自己按指数退避算 |
| 4 | 最多发 3 次(首次 + 2 次重发),写死不给调 |
| 5 | 拿到任何响应 → 返回**那个原生 `Response`**;一个都没拿到 → **抛异常**,重试过则带次数 |
| 6 | 调用**期间**除本次投递自己造的东西外,只在调用方给的信号上挂一个监听器(退避睡眠靠它才能被打断,两条出路都会摘掉);调用**结束后**不持有任何对象、不挂任何监听 |
| 7 | 调用方说「不要了」就停 —— 停在飞的那次投递、不再重试、不把当前那轮退避睡完,**并且已经交出去的那个 `Response`,它的 body 也跟着停** |

**判定题:我正要加的这件事,在这七条里吗?不在 → 它是第八条,不做。** 这条判据也是对抗关的收敛条件:对抗无边界地攻,但每条发现必须追到某一条「没做到」才算真洞;追不到就是在提议第八条,只有 user 能加。

**谁用它**:判据只有一条 —— **打给谁**。打**我们自己后端**的(前端全站 API)继续用 web 那个 axios 单例;打**外部**的(云存储、vendor API、任意网址)走这一层,前后端一致。

**传输层对外只有三个符号**:`httpRequest` · `HttpRetryError` · `MAX_TIMER_MS`(包本身还导出一个退避原语 `exponentialJitterDelay`,见本段末)。**前两个是它做的事,第三个是它对调用方的要求** —— `timeoutMs` 的上界。这一层要求调用方自己算截止时间,却把「必须落在什么范围」只写在一句报错文本里,等于让调用方去猜一个读不到的区间;而按配置算出来的截止时间(`大小 ÷ 速率`)必须能在配置加载时判定会不会超范围,那就得拿得到这个数。**判定题:我要导出的这东西,是让这一层多做一件事,还是把它已经在强制的规则说出口?** 后者才可以。判据、它的词汇表、sleep 留在包内不导出 —— **导出是对别人的承诺**,而这些没有包外消费方。**退避算法曾整体在这份名单上,理由相同,后来那个理由对其中一个过期了**:core 的 BullMQ 重试策略此前留着一份逐字节相同的副本(shared 不能 import core,依赖方向是反的),迁移收尾时它改调这里、副本删掉,**`exponentialJitterDelay` 因此导出**。**规矩没弯,是「没有包外消费方」这个前提对它不成立了** —— 判定题问的始终是有没有真消费方,不是名单曾经写过什么。**它建在 `fullJitter` 上,而那个仍然不导出** —— 成对出现的东西最容易一起放行,但判定题是逐个问的:包外只有一个调用方,就只有一个该出去。**连选项类型都不导出**:它只有 `replaySafe`、`timeoutMs`、`signal` 三个字段,调用方写 `{ replaySafe: true, timeoutMs: 30000 }` 字面量就够,TypeScript 结构化类型自己对得上 —— 导出一个谁都不会拿去声明变量的名字,等于白白撑大包外表面。重试次数与退避基数写死在 `constants.ts`、**故意不做配置**(原先 worker 和浏览器各配一份、已漂移成两种含义)。

**次数只跟着失败走,永不跟着响应走**:拿到 200 的调用方不需要知道试了几次;拿到失败的才需要,用来记一条有意义的日志。所以成功返回光秃秃的 `Response`,失败抛 `HttpRetryError`(带 `attempts`,原始错误在 `cause`)。**第一次就失败、没重试过的,原样抛原始错误不包装** —— `attempts: 1` 只是在说「请求发出去了」,调用方本来就知道。

**调用方声明三件事,判据同一条:这一层能不能从「一个网址 + 一堆字节」里自己推出来?推不出来就得调用方说**。

| 调用方要说的 | 为什么这一层推不出来 |
|---|---|
| `replaySafe`:再送一遍会不会产生第二次副作用 | 只有调用方知道 `POST /predictions` 会多花一次 vendor 的钱,这一层再怎么检查请求也看不出来。**别为「让它更可靠」到处开 true**,那是把含义倒过来用,代价是真金白银付两次 |
| `timeoutMs`:这次最多等多久(可不填,默认 300 秒) | 只有调用方知道这个模型慢、这个文件 2 GB。这一层要么照着填的等,要么用默认值,**自己算是越界** |
| `signal`:还要不要这个答案(可不填) | 只有调用方知道用户点了停止、页面关了、这一轮不做了。这一层看得见的只有一个网址和一堆字节,里面没有「谁还在等」这个信息。**它不是更短的超时,也不替代超时** —— 超时说的是「这一次投递最多花多久」、每次投递重新给;它说的是「这个答案我不要了」、对整个调用有效。两者**每次投递现合成**(`AbortSignal.any`),这样单发的信号不会把后面每次投递还没发出就掐掉 |

**「body 还能不能再发一遍」不归调用方说,这一层自己判**:它是平台事实不是业务事实 —— 一次性的来源被第一次投递吃掉了,第二次拿到的是个空壳,而**空壳的下场按形态分两种,实测**(Node 24,两次都对着记录收到什么的真服务器):`ReadableStream` 抛「body 已被搅动」的类型错误,那个错误看起来像网络故障、于是继续重试,最后调用方拿到的是这个类型错误而不是服务器真正给的状态;**async generator 更糟也更安静 —— 静默发出一个空 body、全程零报错,服务器对着一个丢了内容的请求回了 200**。后者才是这道守卫必须存在的理由:错误类型不对还能查,静默提交一个空请求还被接受,等发现时数据已经没了。判据是「读一次就没了」的两个特征:声明了异步迭代(async generator 和大多数引擎上的 `ReadableStream`),或者有 `getReader`(**Safari 至今没给流实现异步迭代**,只认第一个特征会把 Safari 的流当成可重放)。字符串 / `Blob` / `FormData` / `URLSearchParams` / 普通对象两个都不沾,所以照常重试。**已知的窄边**:一个每次都交出新迭代器的自定义对象其实能重发(实测两次都送到、内容都对),会被这个判据一起挡掉 —— 没修,因为造不出这种调用方,而要认出它得去调调用方自己的代码。

**等待多久由对方定,上限只用来判断等不等**:对方在 `Retry-After` 里报了时间,要么**照它说的等**,要么**根本不等、直接把那个响应交回上层**(响应头里就带着那个数,调用方自己读);中间那个「截断成我们自己的数」是错的 —— 等于假装遵守了一个谁都没同意的约定。上限只有一个(60 秒),它存在只是为了一次调用不会无限期占住调用方 —— **原先按「有没有人在屏幕前等」分两档,那是产品决策,不该在这一层**。对方没说话时才轮到我们自己估(指数退避,唯一允许编数字的地方)。

**读 body 完全不归它管**:读多久、读多大、怎么中断,全是应用层的事。**底层协议本来就处理了超时** —— 实测:Node 自带的 fetch 碰上「发完响应头就装死」的服务器,**301 秒后自己拒绝**(`UND_ERR_BODY_TIMEOUT`)。曾经有过一版 604 行的响应体守卫,已整体删除:它做的正是底层已经在做的,而且它是**唯一**逼着传输层去监听取消信号的东西 —— 监听就得持有对象,那才是当时那个泄漏的根。

**一次投递等多久由调用方定,不填才用默认的 300 秒(user 2026-08-03 拍定,已结)**。**这个值归调用方,不归这一层** —— vendor 的超时按调的哪个模型来、上传的超时按文件多大算,这一层只看得见一个网址和一堆字节,**自己定任何数字都是在替知情的人做决定**。判定题:**这个数,我能从一个网址和一堆字节里推出来吗?推不出来 → 它是参数,不是常量**。

**默认值为什么要存在**:一次请求里有两段**没有任何人兜底** —— 把内容发出去、等对方回应 —— 实测都会无限期挂着(接受了连接然后不吭声的服务器,90 秒后仍在挂)。连接阶段归操作系统管,读响应内容按前面的决定归调用方管,只剩这两段。默认值取 300 秒,是底层客户端自己的默认值,不想这件事的调用方拿到的就是它本来就有的。

**它管的是整个投递(含发送)**,因为这个接口只给一个中止开关、砍的是整个操作,分不开。所以调用方给的那个数要把上传时间算进去。

**取值范围只有一条:1 到 2147483647 毫秒之间的有限数,小数照收**。定时器把接不住的值(无穷大 / 非数字 / 0 / 负数 / 超 32 位)**悄悄改写成 1 毫秒**,那等于把「等够久」翻译成「立刻放弃」,所以在边界上直接拒掉、不花三次投递去发现它。**小数不在此列**:实测 1500.75 在 1500 毫秒触发、300000.5 在 300011 毫秒触发,定时器只是把小数部分截掉。这条曾经写成「必须是整数」,理由是把无穷大那次的实测结论顺手套到了小数头上 —— 而按文件大小算超时(`字节数 ÷ 速率 × 1000`)本来就常出小数,等于把这一层最想服务的那类调用方挡在门外。0.5 仍然被拒,因为它截断后是 0,而 0 正是定时器要改写的值之一。

**教训写在这儿别再犯**:中间有一版把它写死成 10 秒,理由是「每个调用点设的值这一层也知道」——**那句话是假的**,一查就知道十几处 vendor 调用按模型配、上传按文件大小算。写死之后后果不是「慢」而是「不可能」:实测 8 MB 上传打给一个健康的服务器,三次投递全被砍断、一次都没传完;2 GB 视频更是永远传不上去。

**有一个停止开关,但它是可选的,不填时行为跟以前一模一样(user 2026-08-10 拍板加进来)**。

**原先不给这个开关的理由是:调用方不想要答案了就别拿着那个 promise,没人持有的对象本来就会被回收。那句话本身没错,错在它兜不住有人在屏幕前等的场合** —— 丢掉 promise **不会**中止已经跑起来的重试,实测(在服务器端计时、从调用方撒手那一刻算起,跑四轮):第 2 次投递落在 0.3~0.9 秒,第 3 次落在 0.4~2.6 秒。**说不出一对固定的数字**,因为两次等待都是在上限(1 秒、2 秒)以下随机抽的,能说的只有那个上限。兜住它的是第 4 条(最多 3 次)而不是调用方。对**没人等着**的调用(worker 后台任务)这个上限完全够;对**有人等着**的调用不够 —— 用户点了停止,却要等这个调用把剩下的投递和退避走完,那段时间他看着一个已经决定停下的东西继续转。

**所以第 7 条不是推翻那个理由,是那个理由只覆盖了一半场景**。填了 `signal` 的调用按第 7 条停,不填的照旧靠第 4 条兜。

**停要停干净,四处缺一不可**(每一处都有自己的测试,`src/http/__tests__/cancellation.test.ts`):

| 处 | 不做的后果 |
|---|---|
| 每次投递把外部信号与本次超时合成后交给 `fetch` | 信号根本进不来,只是个摆设 |
| 重试判定之前先问一句「还要不要」 | 被掐断的那次投递拿不到响应,重试判定看到的状态码是空的,会跳过所有按状态的早退、一路落到「重试」分支 —— 停一次立刻又开一次 |
| 退避等待能被信号打断 | 已经决定不再重试了,还要先把这轮退避睡完 |
| **进下一圈之前先判一次** | 退避是被打断的那次,信号已经取消了却还会再走一圈:建控制器、建定时器、调一次注定失败的 `fetch`,然后次数变成 2,调用方拿到的是「failed after 2 attempts」这种网络故障的说法,而真实原因(用户停了)被埋在 `cause` 里。**没有多打出去一个请求,坏的是次数** —— 这一条被信号打断时 `web_search` 认得出是用户停了,报的是「用户停止」而不是网络故障 |

**「body 也跟着停」是新加进第 7 条的,它是这一层的承诺,不是巧合(user 2026-08-10 拍板加第 7 件事时一并认下)**。机制:合成信号是在 `fetch` 那一步交进去的,而 `fetch` 在**响应头到达**时就返回了、body 还在流,那个 Response 的 body 从始至终仍受合成信号约束 —— `httpRequest` 返回后,合成信号里「超时」那一半的定时器已经清掉、不会再触发,但「调用方」那一半还活着。实测:发完响应头就装死的服务器,调用方信号触发后 3 毫秒 `res.text()` 被拒,错误就是调用方传进来的那个。

**所以「读 body 完全不归它管」那段要连着这条一起读**:读多久、读多大、读出来怎么解析,仍然全是应用层的事,这一层不碰;它只保证一件事 —— **调用方说不要了,读也会停**。这条写下来是因为已经有人依赖它:`web-fetch` 和 `web-search` 都直接 `res.text()` / `res.json()`,两个工具一行取消代码都没有,靠的就是这条。写之前它是个没人知道的副作用,谁来「修正」这一层让它交出 Response 后真撒手,那两个工具就会静默地卡住。

**第 6 条里那个监听器为什么值得单独写出来**:可打断的退避**在等待期间**往调用方的信号上挂一个监听器,这是它唯一能被打断的方式;两条出路(睡够了 / 被打断)都会把它摘掉。**它格外要紧,因为信号是调用方的、活得比这次调用长** —— 一次调用漏摘一个,调用方每发一次请求就多攒一个。合成信号那一半**观测不到也不需要观测**:`AbortSignal.any` 走的是规范里的 dependent signal,源信号对它是弱引用,实测 `getEventListeners(信号, 'abort')` 在合成前后恒为 0。

**交出去的就是原生 `Response`,交完撒手**:不包装、不代理、没有句柄。**没人持有的对象本来就会被回收,不需要任何「强制释放」的约定**。要中断正在进行的读取用 `response.body?.cancel()`,那本来就是拿到任何 `fetch` 响应后该用的方式,跟这一层无关。

**它自己不写日志(library 边界)**:失败经异常交给上层,上层在 `catch` 里 `logger.error({ err })` —— 异常带的 `attempts` 自动进那条日志。**异常不能被忽略**,不写 `catch` 它会一直往上冒;而返回值里的失败标记,调用方不读就静默丢了。

## 进本包判定题
web **用得到**吗?用得到 → `shared`;用不到 → `core`。

**这条判定题假设只有两种运行时(浏览器 / 后端 node),而 ingest Worker 是第三种**(#173,Cloudflare Workers)。它跟浏览器一样零 node API,**`@breatic/core` 它加载不了** —— 那个包的 import 图里到处是 `node:` 模块。所以 **ingest Worker 要用的东西也放这儿**,哪怕 web 用不到(第一个这样的是 `upload/ticket.ts`:server 签发、Worker 验签,两边同一份签名格式)。判定题因此是两问:**web 用得到吗?ingest Worker 用得到吗?任一为是 → `shared`;两个都不 → `core`**。理由不是「三个运行时」这个说法本身,是**签名格式写两份会漂,漂了之后两边互相拒绝对方的 ticket**。

## 可 import 谁
- ✅ 外部 npm(必须**浏览器安全**:零 `node:*` / `fs` / `async_hooks`,`sideEffects: false`)
- ❌ `@breatic/core` / `@server` / `@worker` / `@collab` / `@web` —— 一个都不行(shared 是最底层)
- 本包内部用 `@shared/*` 前缀

## 暴露啥
**单入口** `src/index.ts`(`tsup` 全 bundle),不开多 subpath 入口(多入口会把 `@shared/*` 泄漏进 dist)。

## 怎么拿配置
不拿。shared 是纯数据/类型层,不读配置、不读 `process.env`、不写日志。

## 守卫
`breatic/no-relative-import`(走别名)· repo-lint 的 `no-unresolved-alias-in-dist`(dist 不漏别名)· `breatic/no-library-env-access`(零 `process.env`)· `breatic/no-library-logger`(零 logger)。
